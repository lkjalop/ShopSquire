## A. Bulk quantity → cart + quantity stepper + "change your mind"

**Symptom (008/009/012):** a "40 business laptops" query adds **qty 1** on *Add*; no stepper; the
`Bundle Savings` "Laptop price" sums whatever is in the cart, confusing the buyer.

**Files + lines**
- `frontend/src/App.tsx:682` — `addToCart = async (sku: string)` → **takes no quantity** (always 1).
- `frontend/src/App.tsx:696` — the "Nice choice!…added" message.
- `frontend/src/App.tsx:1984,2038,2079,2107,2274` — the `Add` buttons call `addToCart(p.sku)`.
- `frontend/src/lib/api.ts:269` — `addCartItem(uid, sku, quantity = 1)` — **already supports qty**.
- `src/app/routers/cart.py:30,41` — `quantity: int = 1` — **backend already accepts qty**. Stock gate
  `_get_stock_level` already present.
- `frontend/src/components/CartPanel.tsx` — cart line rows (need a `−/＋` stepper + Remove).

**Agnostic-core:** all generic commerce (opaque SKU + integer qty). No flavour, no extraction. The one
new rule — "a bulk query's `order_quantity` seeds the default add-qty" — is vertical-blind.

**Wiring**
1. `addToCart(sku, qty = 1)`; pass `qty` to `addCartItem(uid, sku, qty)` (api.ts already forwards it).
2. When the turn's `constraints.order_quantity > 1`, pass it as the default on the recommendation `Add`
   (thread `orderQuantity` from the last `/suggest` response into the `Add` handlers at 1984/2038/…).
3. Cart line stepper in `CartPanel.tsx`: `−/＋` → `addCartItem(uid, sku, delta)` / a new
   `setCartItemQty(uid, sku, qty)` (add a `PUT /api/v1/cart/items/{sku}` that sets qty; `cart.py`
   already has `DELETE /items/{sku}`). This is the "change your mind" control.
4. Show line qty × unit in the bundle so "$7,154" reads as "2 × $629 + 3 × $1,499 + …", not a mystery.

**Test:** vitest on `CartPanel` (stepper up/down, remove); a backend test that
`POST /cart/items {quantity:20}` sets 20 and the stock gate still fires.

## F. Auto-draft the RFQ on buyer commit (so the packet is ready)

**Symptom:** after a buyer confirms sourcing the case sits at `COMMITTED` with **no draft**; the operator
must run a draft step before the packet appears. The buyer was told "procurement notified" — the
operator should find a ready draft.

**Files + lines**
- `src/app/routers/fulfillment_cases.py:600` `commit` endpoint — after the buyer commit, best-effort
  advance `COMMITTED → QUOTE_DRAFTED` by invoking the same path as
  `fulfillment_cases.py:652` `draft-quote` (which fires `external_message_drafted`, `domain.py:146`).
- Draft builder: `src/app/services/fulfillment/draft.py` (agnostic — supplier-private packet, no product
  vocab in the core; product data is opaque).

**Agnostic-core:** the draft rendering is already agnostic. The new "auto-draft on commit" is a
flag-gated (`FULFILLMENT_AUTODRAFT_ON_COMMIT`, default-OFF) best-effort call — no flavour.

**Wiring:** in `commit`, after the state reaches `COMMITTED`, if the flag is on and an approved supplier
exists, call the draft path (reuse the draft-quote service, not the HTTP handler). Keep it best-effort:
a draft failure must not fail the commit. Trace `external_message_drafted`.

## M4→M5. Demand-aware discount (the deck's core execution bridge)

**Symptom:** the market-intel loop is invisible on customer-facing surfaces. `sales_response_policy`
(M4) *recommends* but nothing *consumes* it. This is slide-9/slide-22 of David's deck.

**Files + lines**
- CORE (built, agnostic, in `_CORE_MODULES`): `src/app/services/sales_response_policy.py` +
  `GET /market/sales-response` (`fulfillment_cases.py`).
- CONSUME #1 — margin panel: `src/app/routers/fulfillment_cases.py:296` `margin-advice` endpoint +
  `src/app/services/margin_advisor.py`. Enrich the advice with `assess_sales_response(...)` so the
  recommended discount becomes *demand-aware* ("15% to clear surplus — demand softening" vs "hold —
  rising demand, short stock").
- CONSUME #2 — ranking emphasis: `Product_Ranking_Agent` — apply `promotion_bias` (boost/suppress) as a
  bounded score nudge (surplus items surface; can't-ship shortages recede).
- SURFACE: `src/frontend/admin-react/src/components/procurement/…` (the `op-margin-advice` panel) —
  render the rationale lines.

**Agnostic-core:** `sales_response_policy` is already vertical-blind. **Critical:** the ranking nudge
must stay agnostic — feed a generic `promotion_bias` scalar into the ranker, do NOT inject product
vocab into the ranker core. The margin-advice consumer reads economics + availability + demand findings
(all opaque). Nothing new to excise.

**Wiring**
1. In `margin-advice`, after computing economics, call `assess_sales_response(demand_findings=…,
   availability=…, economics=…)`; attach `sales_response` (action + recommended_discount_pct + rationale)
   to the response. The recommended discount is already margin-clamped by the policy.
2. Gate live application behind the existing adaptive machinery (default-OFF) — Phase-3 "low-risk
   adaptation": recommend in the panel first, apply autonomously later under the confidence gate.
3. Ranker: multiply the candidate score by `1 ± k·promotion_bias` (k small, bias∈{-1,0,+1}); log the
   nudge to the decision trace (`sales_response_applied`).

**Test:** `test_sales_response_policy.py` (done); add a margin-advice test asserting the advice carries
`sales_response` and the discount never exceeds the margin ceiling.
