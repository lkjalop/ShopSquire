## Maintainability assessment

The source-file and Python-function size ratchets both exit zero on C22. **49 maintained files still exceed 1,000 lines.** This means existing ceilings were respected; it does not mean the code is small or maintainable. Python inspection found **2,259 broad-exception-with-pass review candidates** across the snapshot. They need context: optional telemetry failure is different from swallowing persistence, authorization or external-effect errors. The count is not 2,259 proven defects.

Completed extractions separated SQLite compatibility DDL, structured requirement authorization, trace replay helpers and commercial shelf calculations. Four SQLite scenarios retained ordered statements/results/schema, and a dead 95-line frontend alternative was removed. Do not continue with mechanical file splitting or bulk import removal. Prioritize the owner of canonical case transitions, draft versioning, database sessions, provider jobs and typed terminal failures; each boundary needs independent behaviour controls before moving code.

The largest Python spans include `_chat_query_impl` (4,460 lines), `create_app` (2,200 including nested functions), `evaluate_email_security` (2,021), `_route_turn_raw` (1,329), `_recommend_turn` (1,307) and vision `triage` (1,303). `merchant_email_lab` spans 2,328 lines but largely contains markup; treating that span as equivalent control-flow complexity would mislead. The ledger's branch count includes nested functions and is an overapproximation, not cyclomatic complexity.

Refactoring order: establish the typed input/output and owner of each case transition; move pure parsing/commercial reduction behind those contracts; isolate evidence admission and provider calls with deadlines/cancellation; then extract response/trace/UI projections. Preserve original end-to-end expectations, useful positives, rejection controls and latency/resource budgets after each cohort. Move the email lab's static markup separately if it remains a supported tool. Do not introduce a parallel state store, router or memory framework to make the files look smaller.

After C22 was frozen, a separate read-only audit found nine affected packages in the deprecated `src/frontend/storefront-react` install tree. Commit `3c17fe54` retires its package/lock manifests while retaining reference source; both active locks still audit clean. The [retirement receipt](2026-10-25-deprecated-storefront-retirement.md) records scope and hashes. The archived 4,003-line app remains in the C22 inventory and is not presented as another supported frontend.

## Unproved areas that require tests

* “25-unit shortfall”, “shortfall of 25 pieces”, “make it 25 units and draft the shortage email”, delta quantities and references to another case need a full transition-to-draft matrix. A read-only classifier probe found different routing classifications; that is a coverage gap, not proof that canonical quantity was corrupted.
* Natural-language “do not disclose our budget”, multiple draft selection, supplier/recipient changes and ambiguous post-send status need ordinary-chat controls. The reviewed UI disclosure option and saved-version read-through have narrower passing evidence.
* Regional Sydney/Austin/Berlin browser cases preserve currency, budget basis and city text. They do not establish geocoded destination resolution, national tax compliance, approved FX or real supplier availability.
* Allocation unit tests include laptops, chairs and valves. They do not prove that arbitrary categories are enrolled in a merchant catalogue or that non-electronics products complete the deployed journey.
* Indexed Redis/API erasure and restored-memory checks do not cover every case JSON record, attachment, derived image/vector, log, provider copy or backup. Define those retention planes before calling privacy complete.
* Live-model, licensed market-history, citation-entailment and real email-provider tests need declared inputs and credentials. Offline fallback, fixture citations and sandbox dispatch must retain their labels.
* `market-adaptation.spec.ts` navigates the page but asserts API gate fields; its weak-signal step checks confidence without a visible-ranking rejection assertion. That pass does not by itself prove the claimed whole storefront reranking loop. Add DOM outcomes and a complete weak-signal rejection control before making that claim.
