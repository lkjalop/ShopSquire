# ShopSquire pause, retest and roadmap reassessment

Feature work is paused at the user's request. No commit or push is authorized by this report. This assessment supersedes the earlier whole-roadmap interpretation of **9/14 (64.3%)** in the execution ledger. Those were bounded demonstrations, not nine fully closed original workstreams. The distinction matters: the unfinished connections and failure boundaries contain substantial engineering work.

## Assessment

ShopSquire is a substantial fictional-shop prototype with tested services and several real-API browser demonstrations. It is not yet a coherent, release-ready conversational commerce platform. Neither “nothing works” nor “mostly finished” is supported. The strongest evidence is for explicit state, revisions, exact-effect checks and narrow operational workflows. The weakest is for the complete conversational recommendation path, recovery across every effect sink, generalization, and sustained operation.

The roadmap's broad direction was reasonable. The problems were acceptance discipline and integration order: narrower fixtures were counted against broader acceptance criteria; separate showcase screens advanced ahead of the main buyer journey; passing selected tests and a Vite build were too easy to read as platform-wide assurance. The earlier 64.3% statement was too generous as a measure of the original roadmap, and I retract that interpretation. There is no defensible percentage of engineering completion from the current evidence. Synthetic customers, suppliers and transactions are sufficient for this portfolio; real customer access is not a prerequisite. Real-product claims, external-provider operation and commercial readiness remain separate.

## Confirmed defects and review priorities

1. **Buyer evidence UI callback is undefined.** `frontend/src/App.tsx:460` retains the trace tab value without its setter, while `frontend/src/App.tsx:3558` calls `setTraceInitialTab`. The TypeScript failure identifies an actual missing identifier, not merely absent test typings. Exercise the evidence-opening interaction after repair. Other type errors are retained in `storefront-types.log`.
2. **Supplier shortfall is not revalidated against inventory lifecycle changes.** `src/app/services/supplier_enquiry_journey.py:61` validates the case revision; lines 77–81 calculate a shortfall from active holds only. Approval/dispatch at lines 105 and 119 do not recompute it. An isolated fake-transport probe expired a 15-unit hold after approval while retaining the case revision: dispatch still sent the old 15-unit enquiry although 30 units were unheld. A second probe marked 15 units shipped: creating an enquiry reported a 30-unit shortfall instead of the remaining 15. Evidence: `shortfall-probe.json` and reproducible `probe_shortfall.py`. This does not authorize or execute a purchase, but it makes procurement advice obsolete or excessive.
3. **Demo identity is not authenticated buyer identity.** `src/app/routers/product_offer_demo.py:21` accepts caller-supplied `uid`; `src/app/services/case_contract_binding.py:25` compares ownership to that supplied value. The demo gate at `src/app/routers/demo.py:19` checks an enable flag, not deployment environment. These routes must remain isolated until they use authenticated principals or an enforced disposable-demo boundary. Do not describe these fixture journeys as proving general buyer access control.
4. **Tenant enforcement depends on runtime mode.** `src/app/security/auth.py:962` calls centralized membership authorization; it would be wrong to claim that the merchant route has no tenant authorization merely because it lacks a local check. However, `src/app/services/operator_tenant_membership.py:24` defaults local/test environments to audit mode and production to strict mode. Wrong-scope filtering in a local demo is not a substitute for strict credential-to-tenant negative tests in deployment configuration.
5. **Effect coverage is incomplete.** `src/app/services/fulfillment/person_approval.py:120` explicitly permits the legacy no-grant path for contained messages. Case-binding validation at line 102 is conditional on table availability. Existing fake-transport containment must not be generalized to every order, refund, inventory or connector effect. Missing-schema and alternate-dispatch paths need explicit tests.
6. **Boundary and replay semantics need review.** `src/app/services/governed_product_offers.py:126` returns a prior acceptance receipt before rechecking current state, and line 144 imports a cart mutation helper from a router. Historical receipts can be valid, but the UI must distinguish them from current cart truth. Review legacy discount approvals against changed carts and extract a stable transactional cart service when justified. These are review concerns, not reproduced duplicate effects.

The procurement probes also have intentionally failing regression tests in `shortfall-regressions.xml`: two failures, retained for a later repair. They use an in-memory database and fake transport, not the live showcase stock.

### Agnostic core and maintainability

Keep deterministic enforcement for identity, tenant, revision, freshness, money arithmetic, authorization and transaction invariants. Those rules are appropriate safety boundaries. Avoid making product suitability or language understanding depend on accumulating brand/workload-specific branches. Keep configuration facts, compatibility evidence and workload contracts in data/adapters, with unknown/conflicting outcomes and unfamiliar-domain tests.

The current deprecated recommendation edge is already explicitly V2-backed (`src/app/routers/recommend_compat.py:1`, `src/app/services/recommendation_compatibility.py:392`). Adding another recommendation version would not repair the observed integration failures. Scrutinize alternate entry points, shared projections, cancellation and error semantics instead. The expanding demo surfaces and service-to-router imports are maintainability concerns: first consolidate behavior behind existing regression checks, rather than layering more independent orchestrators.

The broad run also caught a concrete core/profile boundary violation: `src/app/services/fulfillment/draft.py:395` contains GPU/VRAM presentation labels in a module described as vertical-blind. Move that vocabulary into a profile/schema presentation adapter; it is not evidence that every core algorithm is electronics-specific. A second architecture test failed because `chat.py`'s counted domain vocabulary **decreased from 17 to 2**: that test requires lowering its recorded ceiling after an improvement. Treating both failures as architectural deterioration would be misleading.

## What can be demonstrated and claimed

Subject to the fresh test results below, the existing demonstrations include multi-turn persisted procurement facts; a fictional requirement contract with explicit qualification/expiry/revocation; accepted stock holds and quantity amendments; operator inventory transactions; independently approved fake supplier enquiries and reviewed structured replies; supported fictional upgrade/accessory proposals with explicit cart acceptance; and a cited, read-only synthetic replenishment decision using local extraction and lexical/dense retrieval.

These are connected in places but distributed across separate surfaces. They do not yet constitute the complete main-chat buyer journey. External research success, real Blender suitability, real supplier communication, real payment execution, production security and sustained stability are not claims supported by this runtime.

I visually inspected the fresh supplier and bundle screenshots. The supplier screen exposes case/enquiry identifiers and raw reply JSON; the bundle screen is a minimal fixture surface. Functional assertions passing does not establish usable operator UX, accessibility, responsive layout or a polished showcase. These should be acceptance checks on the connected journey, not another large feature program. Isolate/reset demo scenarios reproducibly: inventory tests consume real simulated stock, so the current shortfall depends on prior fixture transactions and should not be narrated as a permanently fixed 15 units.

A defensible portfolio description is: “I built and evaluated a simulated agent-assisted electronics shop, using persisted case state, evidence checks, transactional inventory, independent approvals and fake-provider recovery boundaries. I used regression tests and real-API Playwright journeys to verify durable state, and found integration defects through broader testing.” Describe AI-assisted implementation and personally understood/design-reviewed work accurately. Do not claim that every change followed TDD, that all tests pass, or that a workflow file proves operational CI/CD.
