# Effect boundary follow-up

This is a focused review of the remaining commerce paths, not a complete vulnerability assessment. Runtime fixtures disable external payments, clear provider credentials and force fake supplier/ERP transports. Passing fictional workflows do not authorize enabling live commerce.

| Path | Observed implementation | Remaining obligation |
| --- | --- | --- |
| Supplier enquiries | `services/supplier_enquiry_journey.py` binds a case/revision, trusted supplier contact and independent person grant to the outbox. `routers/operator_supplier_enquiries.py` obtains the authenticated operator. | Broader races and trusted provider reconciliation; connecting a buyer-selected estimate to an approved purchase. |
| Buyer quote selection | `services/buyer_supplier_selection.py` stores exact terms/digest and revalidates them. `buyer_supplier_constraints.py` checks current typed budget/deadline constraints. | Selection remains intent only. It does not reserve supplier stock, authorize payment or provide a delivery guarantee. |
| Legacy purchase orders | `services/fulfillment/purchase_order.py:52` checks scope, commits dispatch intent and requires a receipt. The configured live `HttpErpTransport` is blocked because this path lacks a person-bound grant. | Implement authenticated requester/approver ownership and recovery before enabling live dispatch. A blocked live path is not feature completion. |
| Refund request and approval | `routers/payments.py`, `refund_request` and `refund_approve`, record role identities. The service's expiring permit binds amount/currency/intent/idempotency fields. | A role string does not establish two different people. Bind both actions to trusted persons and current tenant membership; validate authority again at execution. |
| Refund worker | `services/payment_reconcile_scheduler.py:34` can call `refund_execution.execute_pending` without an HTTP request. Exact permits and atomic claims exist. | Exercise approval/revocation and crash recovery through this entry point. Do not rely on a route-level switch to govern a worker. |
| Provider execution switch | A new red test showed `StripeClient.create_refund` and `create_payment_intent` could call a mocked SDK despite `PAYMENT_EXECUTION_ENABLED=0`. The shared policy now guards the provider methods as well as the HTTP route. | Verify other payment/connector providers separately. This switch is a deployment control, not buyer consent or distinct-person approval. |
| Legacy refund retry tenant | `routers/payments.py`, `refund_execute`, passes `tenant_id="default"` to the execution service. | Replace the legacy default with authenticated tenant context and verify order ownership; inspect ledger/request/approval endpoints together. This observation alone is not proof of an exploitable cross-tenant request. |
| Order dispatch approval | `routers/payments.py`, `dispatch_approve`, uses an owner-role dependency and passes the role into dispatch. | Person separation, exact approved payload and revocation must be proved for the order-dispatch path, independently of supplier enquiry tests. |
| Completion | `refund_completion.py` accepts successful matching provider receipts; legacy PO completion transitions through workflow state. | Each sink needs an independent completion check, including partial effects and uncertain outcomes. Authorization does not prove completion. |

All paths above are under `src/app/`. [The changed-file index](EXECUTION_CHANGE_INDEX_2026-10-05.md) provides current lengths and entry points; [the execution roadmap](ROADMAP_ALL_EXECUTION_2026-10-05.md) records test results and remaining gates.

The next implementation batch should carry the existing generic person/effect contract through refund and order APIs, services and workers. Avoid adding a second approval mechanism or treating a second credential as a second person. For each sink, test same-person aliases, wrong tenant, changed amount/recipient, expired/revoked grants, concurrent dispatch, crash after provider acceptance and reconciliation without duplicate effects.
